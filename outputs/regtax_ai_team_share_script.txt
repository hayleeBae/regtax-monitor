[슬라이드 1]
오늘은 AI 기술을 깊게 설명하려는 자리가 아닙니다. regtax-monitor에서 AI를 어디에 쓰고, AI가 틀릴 수 있기 때문에 어떤 구조를 넣었는지만 간단히 공유드리겠습니다. 아직 전체 구현이 끝난 상태가 아니므로 최종 성능 리뷰가 아니라 설계 방향 공유입니다.

[슬라이드 2]
AI 모델은 일반 프로그램처럼 항상 같은 정답을 계산하지 않습니다. 대신 긴 법령을 요약하고, 법령 용어와 코드의 의미를 연결하고, 주어진 코드 예시를 바탕으로 수정 초안을 만드는 데 강점이 있습니다. 반대로 없는 파일이나 컬럼을 그럴듯하게 만들 수 있고, 입력이 너무 길면 중요한 앞부분을 놓칠 수 있습니다. 그래서 이 설계는 AI가 잘하는 부분만 사용하고 나머지는 일반 코드로 통제합니다.

[슬라이드 3]
AI가 직접 관여하는 부분은 두 군데입니다. 첫 번째는 법령 변경 전후를 읽고 요약과 영향 분석을 만드는 부분입니다. 두 번째는 관련 코드가 이미 좁혀진 뒤 수정 초안을 만드는 부분입니다. 법령 수집, 실제 파일 검색, diff 생성, 테스트, 승인 같은 작업은 AI가 아니라 일반 코드와 사람이 담당합니다.

[슬라이드 4]
외부 API 모델은 대형 모델을 바로 사용할 수 있어 일반적으로 초기 품질과 속도가 좋습니다. 하지만 내부 코드 스니펫을 외부로 보내는 검토가 필요하고 토큰 비용이 발생합니다. 로컬 Ollama 모델은 코드가 외부로 나가지 않는 대신 CPU에서는 느리고 복잡한 추론 성능이 낮을 수 있습니다. 이 프로젝트는 보안을 우선해 로컬을 기본으로 선택했지만, LlmClient 인터페이스를 두어 백엔드는 교체할 수 있게 했습니다.

[슬라이드 5]
모델 성능을 보완하는 구조는 네 단계입니다. 먼저 전체 저장소를 주지 않고 RAG, 용어 사전, 상수 값 매칭으로 후보를 좁힙니다. 모델에게 전체 파일을 다시 쓰게 하지 않고 SEARCH와 REPLACE 블록만 만들게 합니다. 이후 시스템이 파일 존재와 원본 앵커 일치를 확인합니다. 마지막으로 실제 저장소가 아닌 복사본에서 git apply와 골든 테스트를 실행하고 사람이 승인합니다. 핵심은 모델이 절대 틀리지 않게 만드는 것이 아니라, 틀려도 실제 코드에 바로 반영되지 않게 하는 것입니다.

[슬라이드 6]
모델 결과는 단계별로 간단히 보겠습니다. 검색에서는 정답 파일이 상위 후보에 있는지, 초안에서는 출력 형식과 앵커를 지켰는지, 적용에서는 git apply가 되는지, 검증에서는 골든 테스트를 통과하는지 봅니다. 마지막으로 사람이 수정 없이 승인했는지와 처리 시간도 기록합니다. 지금은 지표를 정의하는 단계이고, 전체 구현이 끝난 뒤 같은 평가 데이터셋으로 최종 리뷰하겠습니다.

[슬라이드 7]
정리하면 세 가지입니다. AI는 법령을 요약하고 관련 코드의 수정 초안을 만드는 보조 도구입니다. 안전성은 모델 성능이 아니라 검색, 원본 대조, diff, 테스트, 사람 승인 구조가 담당합니다. 실제 성능 평가는 전체 구현이 끝난 뒤 검색 정확도, patch 적용률, 골든 테스트, 사람 검토 지표로 진행합니다. 지금 단계에서는 이 설계 방향만 팀에서 공통으로 이해하면 됩니다.
