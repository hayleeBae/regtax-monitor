[슬라이드 1]
안녕하세요. 오늘은 regtax-monitor가 왜 로컬 모델을 중심으로 설계되었는지, 그리고 로컬 모델의 속도와 성능 한계를 어떤 시스템 구조로 보완하는지 설명드리겠습니다. 핵심은 로컬 모델이 API 모델보다 절대적으로 더 똑똑하다는 주장이 아닙니다. 민감한 eHR 코드를 외부로 보내지 않으면서도, 법령 변경 탐지부터 실제 적용 가능한 패치 초안까지 통제 가능한 방식으로 연결하는 것이 목표입니다.

[슬라이드 2]
먼저 이 프로젝트의 의사결정 기준입니다. 첫 번째 위험은 세법이나 노동법 개정을 놓치는 것입니다. 그래서 수집과 감지에서는 재현율을 우선합니다. 두 번째 위험은 AI가 잘못 만든 코드를 자동으로 반영하는 것입니다. 그래서 모델은 초안까지만 만들고, 파일 확인과 diff 생성, 테스트, 승인은 결정론적 코드와 사람이 담당합니다. 즉 모델 선택도 벤치마크 순위가 아니라 보안, 실패 영향, 운영 통제 가능성을 기준으로 봅니다.

[슬라이드 3]
두 방식의 장단점은 명확합니다. API 방식은 대형 모델을 바로 사용할 수 있어 초기 품질과 구축 속도가 좋습니다. 반면 코드 스니펫이라도 외부 전송 검토가 필요하고, 사용량에 따라 비용이 증가하며 모델 버전 변화의 영향을 받습니다. 로컬 방식은 초기 구축과 운영이 필요하고 CPU에서는 느리지만, 코드가 외부로 나가지 않고 모델과 데이터 버전을 고정할 수 있습니다. 이 프로젝트는 내부 eHR 코드와 매년 반복되는 업무라는 특성 때문에 로컬형을 기본으로 선택하되, LlmClient 인터페이스를 통해 API형을 대체 옵션으로 남깁니다.

[슬라이드 4]
최종 구조에서 모델은 자유롭게 저장소를 돌아다니는 에이전트가 아닙니다. 법령 수집과 정규화, 변경 유형 분류를 거친 뒤, RAG와 용어 사전, 상수 값 매칭으로 관련 코드 후보를 좁힙니다. 모델은 그 코드만 보고 분석과 SEARCH/REPLACE 편집을 생성합니다. 이후 실제 파일 존재 여부, 앵커 일치, unified diff, git apply, 골든 테스트는 일반 코드가 수행합니다. 마지막에는 사람이 승인합니다. 이 구조는 모델이 틀릴 수 있다는 사실을 전제로 안전성을 만듭니다.

[슬라이드 5]
로컬 모델에서는 모델 이름만 바꾸는 것으로 품질이 보장되지 않습니다. 특히 Ollama 컨텍스트 길이가 중요합니다. 4096으로 실행했을 때 프롬프트 앞부분이 잘려 도메인 오해석과 형식 오류가 발생했고, 16384로 올린 뒤 프롬프트 유실이 사라졌습니다. 요약과 코드 편집의 모델을 분리하고, Qwen3 thinking을 끄며, 낮은 temperature와 구조화된 출력 형식을 사용합니다. 또한 운영 수준에서는 모델, 프롬프트, 컨텍스트, 코드 commit을 함께 기록해야 같은 결과를 재현할 수 있습니다.

[슬라이드 6]
속도와 성능 단점은 세 가지로 보완합니다. 첫째, 전체 파일을 읽히지 않고 코드 구조 단위로 청킹해 필요한 후보만 검색합니다. 둘째, 전체 파일을 다시 쓰게 하지 않고 정확한 SEARCH/REPLACE 블록만 만들게 합니다. 앵커가 틀리면 실제 원본 주변만 다시 제공해 재시도합니다. 셋째, 모델이 diff를 직접 확정하지 못하게 하고 서버가 diff를 만든 뒤 스크래치에서 적용과 테스트를 수행합니다. 결과적으로 모델의 토큰 사용과 자유도를 줄이고, 오류가 실제 저장소에 영향을 주지 않게 합니다.

[슬라이드 7]
모든 변경에 같은 자동화 수준을 적용하면 안 됩니다. 기존 숫자, 비율, 날짜 변경은 상수 매칭과 골든 테스트가 잘 작동하기 때문에 초안 자동화에 적합합니다. 조건과 표 변경은 위치 매핑은 가능하지만 의미 검토가 필요합니다. 새 필드나 구조 개정은 분석과 영향 범위 제시에 집중하고 코드 초안 생성을 제한합니다. 최종 설계에서는 변경 유형과 신뢰도에 따라 초안 허용, 수동 검토 필수, 분석 전용 정책을 반환합니다.

[슬라이드 8]
성능은 모델 응답의 인상으로 평가하면 안 됩니다. 탐지에서는 놓치지 않는지, 검색에서는 정답 파일이 top-k 안에 들어오는지, 생성에서는 출력 형식과 앵커가 맞는지, 최종적으로 git apply와 골든 테스트를 통과하는지 봅니다. 그리고 사람이 수정 없이 승인했는지, 수정에 얼마나 시간이 들었는지도 측정합니다. 운영 측면에서는 tokens per second, p50과 p95 지연, 타임아웃, 메모리를 기록합니다. 이 지표들을 변경 유형별로 분리해야 수치 변경의 높은 성공률이 구조 변경의 실패를 가리는 일을 막을 수 있습니다.

[슬라이드 9]
평가 방법은 historical replay입니다. 과거 법령 개정 시점의 원문과 당시 코드 commit을 고정한 뒤, 검색 전략과 모델을 바꿔가며 같은 문제를 다시 풉니다. RAG 단독, 용어 사전 추가, 상수 매칭 추가, 검증 매핑 추가의 효과를 분리해 측정합니다. 8B와 14B, 4K와 16K 컨텍스트도 같은 데이터셋에서 비교합니다. 각 실행은 run_id로 묶고 입력과 출력 hash, 검색 근거, patch, 테스트 로그, 사람 판정을 저장해 재현 가능하게 만듭니다.

[슬라이드 10]
데이터가 쌓이면 가장 먼저 좋아지는 것은 모델 파라미터가 아니라 검색 경로입니다. 첫 시즌에는 RAG, 용어 사전, 상수 매칭으로 후보를 추정하고 담당자가 맞는 위치를 검증합니다. 다음 시즌 같은 조문이 바뀌면 검증된 파일과 심볼로 바로 갈 수 있어 검색 정확도와 속도가 동시에 개선됩니다. 승인, 거절, 골든 테스트 결과가 쌓이면 변경 유형별 threshold와 후보 랭킹을 조정할 수 있습니다. 충분한 고품질 편집쌍이 확보된 뒤에야 reranker나 선택적 fine-tuning을 검토합니다. 현재는 데이터가 없기 때문에 몇 퍼센트 좋아진다고 보장할 수 없으며, historical replay로 학습 곡선을 측정해야 합니다.

[슬라이드 11]
정리하면, 이 프로젝트의 완성 기준은 더 큰 모델을 붙이는 것이 아닙니다. 모든 실행을 측정할 수 있고, 같은 조건에서 재현할 수 있으며, 변경 유형에 따라 자동화 범위를 통제하고, 사람이 근거를 보고 승인할 수 있어야 합니다. 로컬 AI는 법령을 이해하고 관련 코드를 좁혀 검토 가능한 수정안을 제시합니다. 실제 반영 권한은 끝까지 시스템과 사람에게 남깁니다. 이것이 보안이 중요한 기업 환경에서 로컬 모델을 실용적으로 사용하는 방식입니다.
