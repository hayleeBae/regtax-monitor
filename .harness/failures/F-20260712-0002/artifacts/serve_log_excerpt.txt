# 초안 생성 출력 절단 — max_tokens 상한 도달로 제안 원문 공백 반환
#
# 당시 조건:
#   - 생성 모델: qwen3:8b (LLM_BACKEND=local, Ollama, M1 맥북)
#   - max_tokens=4096 (propose/complete 기본값)
#   - M1 생성 속도 약 5–8 tokens/s
#   - F-20260712-0001(num_ctx 4096 초과)과는 별개 실패 모드 — truncated=0,
#     즉 컨텍스트 창은 초과하지 않았고 "출력" 쪽 상한이 문제
#
# 증상 타임라인:
#   1차 시도 — httpx 600초 타임아웃으로 클라이언트 측 중단, 서버는 생성을 계속해
#             10분 이상 소요 후 500 반환
#   2차 시도 — 생성이 max_tokens=4096 상한에 도달해 EOS 미도달 상태로 중간 절단.
#             응답에 완결된 @@@FILE/@@@SEARCH/@@@REPLACE 블록이 없어
#             파서(app/llm/common.py)가 편집 블록을 추출하지 못하고
#             제안 원문이 공백으로 반환됨
#
# serve 로그 관련 라인 발췌 (사용자 제공 — ollama serve가 포그라운드 실행이라
# 파일 로그가 없어 터미널 출력에서 확보한 조각):
#
#   n_decoded=4096            ← 출력 토큰이 max_tokens 상한까지 생성됨
#   truncated=0               ← 컨텍스트 창(num_ctx) 초과는 아님 (EOS 미도달 절단)
#   [GIN] 500 | 10m0s         ← 1차 시도: 10분 경과 후 500 (httpx 타임아웃 600s와 일치)
#
# 원인 분석 — ⚠ 미검증 가설 (verified_cause에는 기록하지 않음):
#   @@@SEARCH/@@@REPLACE 출력 형식은 수정 대상 원본 섹션을 SEARCH 블록과 REPLACE
#   블록에 사실상 2회 복제하게 만든다. 수정량과 무관하게 출력 토큰이 원본 크기의
#   2배로 구조적으로 폭발하며, 5–8 t/s에서 4096토큰 생성만으로 약 8.5–13.7분이
#   소요된다 → 타임아웃(부가 증상)과 상한 절단(주 증상)이 같은 뿌리에서 나옴.
#
# 후속 조치 연결:
#   이 레코드는 출력 형식을 구조화 JSON(원본 복제 없이 위치 참조 + 교체 내용만
#   출력)으로 바꾸는 개선 작업의 직접 근거다. 가설이 맞다면 형식 전환으로
#   출력 토큰이 절반 이하로 줄어 두 증상 모두 해소되어야 한다 — 전환 후 동일 건
#   재현으로 검증하고 verified_cause를 채울 것.
