마이그레이션/리팩토링 결과물이 원본의 동작을 보존하는지 검증(audit)하라. 이 작업은 **읽기 전용**이다 — 코드를 수정하지 않는다.

## 입력

사용자가 지정하지 않았다면 물어봐라:

- **원본**: 검증 기준이 되는 소스 (파일/디렉토리 경로, 또는 레거시 시스템의 해당 모듈)
- **대상**: 검증할 신규 코드 (파일/디렉토리 경로)
- **범위**: 전체 / 특정 모듈·화면·기능

## 검증 절차

1. 원본과 대상을 모두 정독한다. 추측하지 말고 실제 코드를 근거로 판단하라.
2. 항목별로 대조한다:
   - **비즈니스 로직**: 계산식, 분기 조건, 절사/반올림, 날짜 경계 처리
   - **데이터 흐름**: 입력 → 변환 → 저장/출력 경로가 동일한가
   - **유효성 검사**: 원본의 validation 규칙이 모두 이식되었는가 (조건의 부정/우선순위 뒤집힘 주의)
   - **엣지 케이스**: null/빈값, 다계열사 분기(company_id 등), 권한별 분기
   - **누락**: 원본에는 있는데 대상에 없는 기능
   - **초과**: 원본에 없는데 대상에 추가된 동작 (임의 "개선" 포함)
3. `bash scripts/verify.sh full`을 실행해 컴파일/테스트 상태를 확인한다.

## 출력 형식

```markdown
# Audit Report: {범위}

## 요약
- 검증 항목 N개 / 일치 N개 / 불일치 N개 / 판단 불가 N개

## 불일치 상세
| # | 항목 | 원본 (파일:라인) | 대상 (파일:라인) | 차이 | 심각도(H/M/L) |
|---|------|----------------|----------------|------|--------------|

## 판단 불가 항목
{원본 접근 불가, 동적 동작이라 정적 분석으로 확인 불가 등 — 사유와 함께}

## 개선 제안 (참고용 — 이번 audit에서 수정하지 않음)
```

## 금지사항

- 발견한 문제를 이 자리에서 수정하지 마라. 이유: audit과 수정을 분리해야 리뷰가 가능하다. 수정은 사용자 승인 후 별도 step으로 진행한다.
- "아마 맞을 것"이라는 표현으로 얼버무리지 마라. 확인 못 했으면 "판단 불가"로 분류하고 사유를 적어라.
