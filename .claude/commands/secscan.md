이번 변경분(또는 사용자가 지정한 범위)에 대해 보안 점검을 수행하라. 이 작업은 **읽기 전용**이다 — 발견한 문제를 이 자리에서 수정하지 않는다.

## 절차

### 1. 자동 점검

```bash
bash scripts/verify.sh security
```

(시크릿 스캔 + 스택별 의존성 취약점 점검. 실패 항목은 리포트에 포함)

### 2. 수동 코드 점검 — 변경된 파일을 정독하며 아래를 확인

**입력 처리**
- [ ] 외부 입력(요청 파라미터, 파일 업로드, 헤더)이 검증 없이 사용되는 곳
- [ ] SQL: 문자열 연결로 쿼리를 만드는 곳 (매퍼/프로시저 파라미터 바인딩 확인. iBatis `$...$` 치환은 인젝션 위험 — `#...#` 바인딩인지 확인)
- [ ] 경로 조작: 사용자 입력이 파일 경로에 들어가는 곳

**인증/인가**
- [ ] 새 엔드포인트/화면에 권한 체크가 있는가
- [ ] 다계열사/조직 스코프: 다른 company_id·org의 데이터를 조회할 수 있는 우회 경로 (IDOR)
- [ ] localhost/개발용 인증 우회 코드가 운영 빌드에 포함될 가능성

**데이터 보호**
- [ ] 개인정보(주민번호, 계좌, 급여 등)가 로그에 남는 곳
- [ ] 민감 데이터의 평문 저장/전송
- [ ] 하드코딩된 시크릿, 커밋된 .env

**설정/의존성**
- [ ] CORS, 쿠키 플래그(HttpOnly/Secure), 디버그 모드 잔존
- [ ] `NODE_TLS_REJECT_UNAUTHORIZED=0`, `verify=False` 같은 TLS 무력화 코드
- [ ] 의존성 취약점 (1번 자동 점검 결과)

### 3. 리포트 출력

```markdown
# Security Scan Report: {범위} ({날짜})

## 요약
- 자동 점검: 통과/실패
- 발견: Critical N / High N / Medium N / Low N

## 발견 사항
| # | 심각도 | 항목 | 위치 (파일:라인) | 설명 | 권고 조치 |
|---|--------|------|----------------|------|----------|

## 점검했으나 이상 없음
{확인한 체크리스트 항목 — "안 봤음"과 "봤는데 문제없음"을 구분하기 위해 기록}

## 수용된 리스크 (사용자 확인 필요)
{수정하지 않고 넘어가기로 한 항목과 사유}
```

리포트를 `docs/security/scan-{YYYYMMDD}.md`로 저장한다.

### 4. 게이트

- Critical/High가 있으면 배포 진행 불가를 명시하고, 수정 step 설계를 제안하라.
- Medium/Low는 사용자가 수용 여부를 결정한다.

## 금지사항

- 문제를 이 자리에서 수정하지 마라. 이유: 점검과 수정을 분리해야 재점검이 가능하다.
- 확인하지 못한 항목을 "이상 없음"에 넣지 마라. "점검 불가"로 사유와 함께 분류하라.
