이 하네스를 현재 프로젝트에 맞게 셋업하라. 아래 절차를 순서대로 진행한다.

## 1. 인터뷰

사용자에게 다음을 질문하고 답을 받아라 (이미 대화에서 확인된 정보는 다시 묻지 마라):

1. 프로젝트명과 한 줄 목표
2. 프로젝트 유형: 신규 개발 / 기존 코드 유지보수 / 마이그레이션(동작 보존)
3. 기술 스택 — `profiles/` 안의 프로파일 중 해당하는 것 (node-ts / java-spring / python / react-native-expo / 그 외 직접 명시)
4. 테스트 현황: 테스트 있음 / 없음(컴파일 검증만) / 이번에 도입 예정
5. UI가 있는 프로젝트인가? (없으면 docs/UI_GUIDE.md 삭제 제안)
6. 팀 프로젝트인가? (인원, 브랜치 전략, CI 사용 여부)
7. 배포가 있는가? (환경, 자동/수동)
8. 도메인 특이사항 (다계열사 분기, 금액 절사 규칙, 레거시 연동 등)

## 2. 파일 채우기

인터뷰 결과로 다음을 수행한다:

1. **CLAUDE.md** — 프로젝트 유형 선택, 선택한 프로파일의 "기술 스택"·"명령어"·"CRITICAL 규칙 후보" 섹션을 반영. 도메인 컨텍스트 작성.
2. **scripts/verify.sh** — 프로파일의 verify.sh 블록으로 placeholder를 교체. 테스트 유무에 따라 커맨드 조정. 교체 후 `bash scripts/verify.sh quick`과 `full`을 각각 실제 실행해 동작을 확인하라. 실패하면 원인을 사용자에게 보고하라 (임의로 검증을 약화시키지 마라).
3. **docs/PRD.md, ARCHITECTURE.md, ADR.md** — 인터뷰 내용으로 초안 작성. 기존 코드가 있는 프로젝트면 코드를 먼저 읽고 현재 구조를 ARCHITECTURE.md에 사실대로 기록하라 (희망 구조가 아니라 현재 구조).
4. **docs/UI_GUIDE.md** — UI 없는 프로젝트면 삭제.
5. **docs/DEPLOY.md** — 배포 있는 프로젝트만 환경/절차/롤백을 채운다. 없으면 삭제.
6. **.github/workflows/ci.yml** — 팀/CI 사용 시 프로파일의 CI 블록으로 셋업 step을 채운다. CI 미사용이면 삭제.
7. **verify.sh security** — 프로파일의 security 블록 추가. `bash scripts/verify.sh security` 실행 확인.
8. **profiles/** — 선택하지 않은 프로파일은 남겨둬도 무방하다 (삭제하지 마라. 다른 프로젝트에서 재사용).

## 3. 완료 보고

- 채워진 파일 목록과 각 파일의 핵심 결정사항을 표로 요약
- verify.sh 실행 결과
- 사용자가 직접 확인/수정해야 할 항목 (CRITICAL 규칙 최종 확정 등)

## 금지사항

- 인터뷰 없이 임의로 값을 채우지 마라. 이유: 하네스의 가드레일은 사용자가 확정한 규칙이어야 의미가 있다.
- 기존 프로젝트의 소스 코드를 이 단계에서 수정하지 마라. 이유: /setup은 하네스 구성만 담당한다.
