구현에 앞서 설계 단계를 진행하라. 이 단계의 산출물이 승인되기 전에는 코드를 작성하지 않는다.

## 절차

### 1. 현황 파악

- 신규 프로젝트: 사용자와 요구사항을 논의한다.
- 기존 코드가 있는 프로젝트: 코드를 먼저 읽고 현재 구조를 파악한다. 문서와 코드가 다르면 코드를 기준으로 보고한다.

### 2. 설계 산출물 작성/갱신

| 산출물 | 내용 | 게이트 기준 |
|--------|------|------------|
| `docs/PRD.md` | 목표, 사용자, 핵심 기능, 제외 범위, 제약 | 기능 목록에 애매한 항목이 없을 것 |
| `docs/ARCHITECTURE.md` | 디렉토리 구조, 레이어 규칙, 데이터 흐름, 외부 연동 | 새 코드가 어디에 놓일지 즉답 가능할 것 |
| `docs/ADR.md` | 기술 선택과 트레이드오프 | 이번 작업에 영향 주는 결정이 모두 기록될 것 |
| `docs/DEPLOY.md` | 배포 대상 환경, 방식, 롤백 | 배포가 있는 프로젝트만. 환경 목록이 확정될 것 |

### 3. 설계 리뷰 요청

작성/변경된 설계를 요약해 사용자에게 제시하고 **명시적 승인을 받아라**. 다음을 반드시 포함한다:

- 주요 설계 결정 3~5개와 각각의 근거
- 열려 있는 질문 (결정 못 한 것)
- 보안 관점 사전 검토: 인증/인가 경계, 민감 데이터 취급 여부, 외부 입력 지점 — 설계 단계에서 미리 표시해두면 /secscan 때 점검 대상이 된다

### 4. 승인 후

- 승인된 설계를 docs에 확정 커밋한다 (`docs(design): ...`)
- 팀 프로젝트라면 이 커밋을 PR로 올려 팀 리뷰를 받는 것을 권장한다
- 이후 /harness로 step 설계 단계로 넘어간다

## 금지사항

- 설계 승인 전에 구현 코드를 작성하지 마라. 이유: 설계 게이트가 무의미해진다.
- "나중에 정하죠"로 넘어간 항목을 임의로 결정하지 마라. 열린 질문 목록에 남겨라.
