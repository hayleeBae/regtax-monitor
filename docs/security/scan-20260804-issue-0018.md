## 점검했으나 이상 없음

- **원본 repo 훼손 (CLAUDE.md CRITICAL)**: `ALLOWED_SUBCOMMANDS`가 `checkout`/`reset`/`clean`/`commit`/`push`/`fetch`/`clone`을 전부 거부한다(probe로 `checkout main` REJECT 확인). `worktree`는 `add`/`remove`/`prune`만 허용. `worktree add --detach`로 브랜치·HEAD를 움직이지 않는다. 실행 전후 `git worktree list`·`git status --short`가 동일함을 직접 확인했고, 테스트에도 원본 `status`/`HEAD`/`worktree list` 불변 단언이 있다.
- **생성 diff의 적용 범위**: `_apply_in_worktree`는 `cwd=worktree`로 고정해 `apply --check` → `apply` 순으로 실행하며, **원본 repo에 적용하는 경로가 존재하지 않는다**(CLAUDE.md CRITICAL — 자동 적용 금지). patch 임시 파일은 시스템 임시 디렉토리에 만들고 `finally`에서 삭제해 사용자 repo에 남기지 않는다.
- **명령 주입**: `git_cmd.py`의 `subprocess.run`은 **1곳뿐**이고 `shell=False` 고정, 모든 호출에 timeout(기본 120초). `validate_git_args`를 우회하는 공개 함수(`run_raw` 류)가 없고 얇은 헬퍼도 전부 `run_git` 경유. `golden_exec.py`도 `shell=False` + `cwd=worktree` 고정이며 `app/golden.py`(shell=True)를 import하지 않는다.
- **golden_command 인자 재지정 (#0017 발견 #1 해소)**: `validate_golden_args`가 절대경로 인자(`--opt=/abs` 값 포함), `..` 경로 구성요소, 대상 재지정 옵션(`-f --file -p --plugin -C --project-dir --rootdir -b --build-file --settings -s`)을 거부한다. 판정은 정확 이름 또는 `이름=` 접두만 보므로 `--fail-fast` 같은 정상 옵션이 오탐되지 않는다. 실행파일은 `loader.py`의 `GOLDEN_COMMAND_ALLOWLIST`를 **import해 재확인**(복제 없음)하여 로더를 거치지 않은 호출 경로도 방어한다.
- **환경 리다이렉션**: `git_cmd._git_env()`와 `golden_exec`가 상속된 `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`을 제거한다 — 이 값들이 남아 있으면 worktree 안의 작업이 실제 저장소로 리다이렉트된다.
- **임시 디렉토리 정리**: `replay_worktree`가 `finally`에서 `worktree remove --force` → `worktree prune` → 임시 root 삭제를 수행하고, 삭제 전 `tempfile` root 하위인지 확인한다. 예외 주입 테스트로 고정되어 있다. cleanup 실패는 원래 예외를 삼키지 않는다.
- **코드 반출 금지 (CLAUDE.md CRITICAL) — 실측 검증**: `--privacy-mode metadata_only`로 실제 리포트를 생성해 파일 내용을 문자열 검색한 결과 파일 경로(`src/main`, `MinimumWageValidator`, `README`) 0건, 코드 값(`10030`, `150000`) 0건, diff 본문(`diff --git`) 0건. `allowed_artifacts`에 `['count','hash','metric']`만 기록된다. 게이팅은 화이트리스트 구성(허용된 종류만 payload에 넣음)이며 저장은 `report.py` 한 곳에서만 이루어진다.
- **회사 경로 유출**: `worktree.resolve_repo_path`가 `path_env`를 해석하되 오류 메시지에 절대경로를 넣지 않고 환경변수 **이름**만 노출한다. `runner`의 `repo_id`는 절대경로가 아니라 `case_id:sha256(경로)[:16]` 형태라 캐시 키·리포트로 경로가 새지 않는다. `assert_clean_worktree`는 dirty 파일명 대신 건수만 보고한다. `answer_diff`의 `AnswerDiffError`도 절대경로·stderr를 담지 않는다.
- **경로 조작**: fixture 경로는 #0017 로더가 절대경로·`..`를 거부하고, `answer_diff`는 POSIX 정규화 후 구분자 경계 기준으로 매칭한다. `show <rev>:<path>` 형태라 path가 옵션으로 해석될 여지가 없다.
- **승인 게이트 (CLAUDE.md CRITICAL)**: 초안 승인·patch 파일 출력 기능 미추가. replay는 측정 도구이며 `apply`/`approve` 흐름을 건드리지 않는다.
- **실패 격리**: 파이프라인 예외를 `except Exception`으로 케이스 단위에 가두고 `failure_kind` 고정 어휘(`commit_not_found`/`worktree_failed`/`pipeline_failed`/`answer_diff_failed`/`cleanup_failed`)로 기록한다. 고정 어휘이므로 예외 메시지가 리포트로 새지 않으며, 모든 privacy 모드에서 저장 가능하다.
- **인증/인가**: 신규 엔드포인트·라우트 0건. FastAPI·DB를 건드리지 않는다.
- **개인정보·로그**: 개인정보를 다루는 경로 없음. 로깅은 `logger.warning`으로 상황만 남기고 경로·코드를 담지 않는다.
- **시크릿·설정**: 하드코딩 시크릿·커밋된 `.env` 없음. 신규 설정 항목 0건. CORS·쿠키·디버그·TLS 무력화 변경 0건.
- **의존성 변경**: `requirements.txt`/`requirements-dev.txt` **무변경**(diff 0줄). 발견 #1은 이번 변경과 무관하다.

## 점검 불가

- **CVE 등급 판정 (발견 #1)**: 오프라인 환경이라 CVE-2026-59881·69243·69244·69247의 CVSS/심각도를 확인할 수 없다. `pip-audit` 출력에 등급이 포함되지 않는다. 따라서 이 항목이 프로젝트 게이트 규칙("Critical/High 시 중단")에 걸리는지 **판정하지 못했다**.
- **회사 환경에서의 worktree 동작**: 실제 eHR repo(대형, CP949)에서 `worktree add` 소요 시간·`.git/worktrees` 잔여 여부는 집 환경에서 확인할 수 없다.

## 수용된 리스크 (사용자 확인 필요)

- **발견 #2 (Medium)**: 현재 도달 경로가 없어 즉시 위험은 아니나, 보안 경계로 선언한 모듈의 차단 범위가 선언과 어긋난다. 수정 비용이 낮으므로(상수 2개에 항목 추가 + 회귀 테스트) 이번 브랜치에서 처리할 것을 권한다.
- **`.git/worktrees/` 메타데이터 쓰기**: ADR-011에서 이미 수용한 항목. 원본 작업 트리·커밋·refs는 불변이며 `remove`/`prune`으로 회수된다.
- **허용 도구가 대상 repo 코드를 실행하는 것**: `mvn`/`gradle`/`pytest`는 replay 대상 repo의 빌드 스크립트·conftest를 실행한다. "과거 시점 코드에서 골든 테스트를 돌린다"는 기능의 본질이며 대상 repo 신뢰를 전제로 수용한다(#0017에서 수용된 항목과 동일).
